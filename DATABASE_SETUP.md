# Установка и перенос PostgreSQL

## Что теперь делает проект

При запуске `main.py` бот:

1. подключается к PostgreSQL по `DATABASE_URL`;
2. берёт advisory-lock, чтобы две копии не применяли миграции одновременно;
3. создаёт таблицу `public.schema_migrations`;
4. применяет новые файлы из `db/migrations` строго по порядку;
5. проверяет SHA-256 уже применённых миграций;
6. запускает polling только после успешного обновления схемы.

Если миграция не прошла, бот не продолжает запуск на полусломанной базе.

## Чистая установка на Windows

### 1. Создать базу и пользователя

Открой `psql` от пользователя `postgres` и выполни:

```sql
CREATE ROLE auction_bot WITH LOGIN PASSWORD 'замени_пароль';
CREATE DATABASE auction_bot
    WITH OWNER = auction_bot
         ENCODING = 'UTF8';
```

Расширение `pg_trgm` создаётся первой миграцией. Пользователь базы должен иметь право устанавливать это расширение. Если PostgreSQL запретит создание расширения, один раз выполни под `postgres`:

```sql
\c auction_bot
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

### 2. Подготовить окружение проекта

В PowerShell из каталога проекта:

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
Copy-Item .env.example .env
```

Заполни `.env`. Минимально нужны:

```dotenv
BOT_TOKEN=...
DATABASE_URL=postgresql://auction_bot:замени_пароль@localhost:5432/auction_bot
DB_AUTO_MIGRATE=1
```

Для UID-проверок обязательно перенеси прежние `UID_HASH_KEY` и `UID_ENC_KEY`. Новые ключи не смогут расшифровать старые значения.

### 3. Проверить миграции отдельно

```powershell
python -m db.migrator
```

Успешный повторный запуск должен вывести, что схема уже актуальна. После этого:

```powershell
python main.py
```

## Перенос существующей базы на другой компьютер

Миграции переносят **структуру**, но не живые данные. Пользователи, ставки, карточки, аукционы и настройки переносятся штатным форматом PostgreSQL.

### На старом компьютере

Убедись, что `pg_dump` доступен в `PATH`, затем:

```powershell
.\scripts\backup_database.ps1
```

Полученный файл появится в `backups\auction_bot_YYYYMMDD_HHMMSS.dump`.

### На новом компьютере

1. Установи PostgreSQL.
2. Создай пустую базу и пользователя.
3. Заполни `.env` новым `DATABASE_URL`.
4. Скопируй `.dump` в проект.
5. Восстанови данные:

```powershell
.\scripts\restore_database.ps1 -BackupFile .\backups\auction_bot_YYYYMMDD_HHMMSS.dump
python -m db.migrator
python main.py
```

`pg_restore` восстанавливает корректный дамп расширений PostgreSQL. Не нужно копировать вручную функции `set_limit`, `gtrgm_*`, операторы и operator class из текстового дампа: всё это принадлежит `pg_trgm`.

## Как добавлять следующие изменения базы

Создай новый файл, например:

```text
db/migrations/005_add_deck_media.sql
```

Правила:

- номер всегда больше предыдущего;
- применённые файлы не редактировать;
- одна логическая задача на один файл;
- миграция должна быть безопасной в транзакции;
- после создания проверить командой `python -m db.migrator` два раза.

Контрольные суммы намеренно не позволят тихо переписать историю схемы. Для нового изменения создаётся новый файл, а не исправляется уже применённый.

## Старые `init_db.sql` и `db.sql`

Они исключены из переносимой сборки. Старый `init_db.sql` не создавал ENUM-типы и функции в правильном порядке, а текстовый дамп пытался вручную восстановить внутренности `pg_trgm`. Старый `db.sql` содержал снимок пользовательских данных и не являлся миграцией.

## Исправление получасовых слотов

Миграция `005_fix_auction_slot_duration.sql` устраняет ложные конфликты соседних слотов.
Сетка публикации остаётся получасовой (`17:30–18:00`, затем `18:00–18:30`), а
`end_time` хранится как `start_time + 30 минут 59 секунд`, чтобы ставки принимались
до конца отображаемой конечной минуты. Проверка занятости сравнивает время начала
слота, а не пересечение с дополнительными 59 секундами.

После замены файлов достаточно перезапустить бота. Мигратор применит `005` сам.
