# Рефакторинг, фаза 4

## Результат

Фаза 4 переносит создание, модерацию, публикацию и биржу из набора несвязанных
DB-функций в явные доменные workflow. Все критичные изменения состояния теперь
выполняются с проверкой текущего статуса, а конкурентные обработчики не могут
молча обработать одну заявку дважды.

## Поддерживаемые типы аукционов

| Тип | Кто может создать | Правило ставок | Определение результата |
|---|---:|---|---|
| Стандартный | все | ставка растёт | максимальная ставка |
| Обратный | Лакшери 1+ | ставка уменьшается с заданным шагом | минимальная ставка |
| Быстрый | Лакшери 2 | ставка растёт | максимальная ставка |
| Свободный | Лакшери 2 | произвольные комментарии | ручная проверка модератором |
| Чёрный | Лакшери 2 | ставка растёт; участник должен быть Лакшери | максимальная ставка |
| Биржа | все | фиксированная заявка | отдельный workflow биржи |

Уровень проверяется дважды: при показе меню и повторно перед записью заявки.
Подделанный callback не даёт доступ к закрытому типу.

## Архитектура

- `bot/domain/auctions/`
  - канонические `AuctionKind`, `AuctionStatus`, `ExchangeStatus`;
  - правила доступа, ставок и переходов состояния;
  - ожидаемые доменные ошибки вместо неразличимых `Exception`.
- `bot/repositories/auction_workflows.py`
  - транзакционное создание заявки вместе с владельцем;
  - атомарное одобрение, перенос, отклонение и отмена;
  - блокировка слота через advisory lock;
  - claim публикации через `FOR UPDATE SKIP LOCKED`;
  - owner-scoped редактирование и отмена.
- `bot/repositories/exchanges.py`
  - batch и все позиции создаются в одной транзакции;
  - модерация разрешена только из `pending`;
  - публикация использует отдельный claim;
  - удаление мягкое и сохраняет аудит.
- `bot/services/auction_workflows.py`, `bot/services/exchanges.py`
  - единые application services для Bot API, userbot и админки.
- `bot/handlers/auction/publication.py`
  - публикация вынесена из большого `auctions.py`;
  - доставка, фиксация `message_id`, retry и terminal failure разделены.
- `bot/handlers/auction/kinds.py`
  - меню строится из доменной политики, без второй таблицы уровней.
- `bot/telegram/media.py`
  - единая отправка photo/video/animation с безопасным fallback.
- `bot/services/admin_thanks.py`, `bot/services/exchange_media.py`,
  `bot/services/luxury.py`
  - общие функции вынесены из handlers; устранён import-time цикл
    `auctions -> admin_actions -> auctions`.

## Исправленные дефекты

1. Обратный аукцион больше не выбирает максимальную ставку и не показывает
   пользователю подсказку обычного аукциона.
2. Свободный аукцион не прогоняет комментарии через числовой валидатор и не
   объявляет автоматического победителя.
3. Автоставки не запускаются для обратного, свободного и биржевого workflow.
4. Чёрный аукцион отклоняет ставки пользователей без статуса Лакшери.
5. Свободный аукцион исправлен с Лакшери 1 на Лакшери 2.
6. Все типы больше не отвечают «пока в разработке» после успешной проверки
   уровня.
7. Создание лота и запись владельца выполняются одной транзакцией.
8. Создание exchange batch и его items больше не оставляет половинчатую заявку.
9. Одновременное одобрение одного временного слота сериализуется в PostgreSQL.
10. Несколько экземпляров бота не публикуют один scheduled-лот одновременно.
11. Ошибка публикации имеет ограниченное число попыток и видимый terminal status.
12. Биржевой пост также резервируется перед отправкой; зависший claim не
    перезапускается вслепую и не создаёт дубль.
13. Модерация одной exchange-заявки возможна только один раз.
14. Пользователь больше не может подменить `lot_id` и изменить или удалить
    чужую pending-заявку.
15. Удаление лота заменено на состояние `cancelled`: владельцы, история и аудит
    не уничтожаются физически.
16. Динамический `UPDATE auctions SET {field}` ограничен runtime-полями;
    пользовательские и административные поля проходят через whitelist сервиса.
17. Старые write-функции создания, статусов, расписания и биржи удалены из
    `db/db.py`, чтобы новый код не мог случайно обойти workflow.
18. Повторные `@require_db_pool` удалены.
19. Удалены повторные top-level определения и дублирующие регистрации handlers,
    включая тройную регистрацию пользовательского варианта оплаты.
20. Сервис финализации больше не импортирует Telegram-handler: объявление
    результата передаётся ему через application composition в `main.py`.
21. Удалён неиспользуемый динамический `update_card_field`; единственный
    оставшийся динамический update аукциона закрыт строгим whitelist runtime-полей.
22. Миграция удаляет устаревшее ограничение «строго 31 минута», которое ломало
    административное продление, и заменяет его общей проверкой порядка времени.
23. Проверка расписания блокирует обе календарные даты для слота через полночь,
    поэтому параллельное одобрение таких лотов также не создаёт пересечений.

## Миграция 004

`migrations/004_auction_workflows.sql` добавляет:

- publication lease, счётчик попыток и диагностику для аукционов;
- полный набор состояний auction workflow;
- согласованную проверку `end_time > start_time` без жёсткой длительности;
- индексы очереди публикации, проверки расписания и reverse-winner;
- moderation/post/delete metadata для биржи;
- состояния `publishing` и `publication_failed` для биржевой публикации;
- уникальность опубликованного Telegram-сообщения;
- поддержку нескольких одинаковых карт в copies-mode.

`init_db.sql` приведён в соответствие для нового развёртывания. Миграция остаётся
идемпотентной, но уже применённые migration-файлы 001–003 менять нельзя из-за
checksum-контроля.

## Проверка

- `python -m compileall -q .` — успешно;
- AST-разбор всех Python-файлов — успешно;
- дубли top-level функций во всех локальных Python-модулях отсутствуют;
- import-time циклы между локальными модулями отсутствуют;
- зависимости `services/repositories -> handlers` отсутствуют;
- 40 доменных и статических regression-тестов — успешно.

Полный интеграционный прогон с Telegram и PostgreSQL требует тестовых токенов,
userbot-сессии и копии рабочей базы; в релизный архив они намеренно не входят.

## Перед развёртыванием

1. Сделать backup PostgreSQL.
2. На копии базы применить миграцию 004 и проверить список неизвестных статусов,
   если миграция остановится на защитной проверке.
3. Проверить лоты в `publishing`, `publication_failed`, `finalizing` и
   `finalization_failed`.
4. Запустить один тестовый лот каждого типа, отдельно проверить reverse/free/black.
5. Проверить конкурентное одобрение одного слота двумя администраторами.
6. Проверить copies-mode биржи и повторное нажатие кнопок approve/broadcast.
