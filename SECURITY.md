# Security policy

## Секреты и runtime-данные

В репозиторий и релизный архив не должны попадать:

- `.env` и любые реальные токены/пароли;
- `*.session*` Telethon — это полноценные учётные данные;
- PostgreSQL dumps, включая исторический `db.sql`;
- backfill CSV, логи, cache и содержимое `var/`.

Храните session-файлы в `RUNTIME_DIR` с ACL только для service account.
При утечке session завершите активную сессию в Telegram и создайте новую. При
утечке bot token отзовите его через BotFather. Исторический `db.sql` содержит
пользовательские/модерационные данные: его следует хранить только в защищённом
backup storage и считать скомпрометированным, если он уже публиковался.

Перед любым восстановлением per-table export запустите
`python scripts/validate_private_dump.py PATH --schema database/pgadmin_schema.sql`.
Валидатор не печатает значения, запрещает DDL/destructive statements и проверяет,
что каждый файл содержит только `INSERT` и пишет только в таблицу с тем же
именем. SQL разбирается с учётом строк, комментариев и dollar-quoting, поэтому
дополнительную команду нельзя спрятать после значения с точкой с запятой.
Он также принимает только форму `INSERT … VALUES` без SQL-функций. Это
защитный фильтр, а не SQL sandbox: восстановление всё равно выполняется только
в изолированной staging/test БД ролью с минимальными правами.

`UID_HASH_KEY` и `UID_ENC_KEY` не логируются и не меняются при обычном deploy.
Ротация требует отдельной миграции с проверкой целостности.

## Legacy HTTP bridge

Мост `POST /notify_bid_deleted` опционален и при импорте приложения не запускает
HTTP-сервер. Если он не нужен, оставьте `LEGACY_BRIDGE_SECRET` пустым: endpoint
будет закрыт с кодом 503. Не используйте этот секрет для других протоколов.

Каждый запрос обязан содержать три заголовка:

- `X-Auction-Timestamp`: каноническое Unix-время в секундах (только десятичные
  цифры, без ведущих нулей);
- `X-Auction-Request-Id`: новый для каждого запроса ASCII nonce длиной до 128
  символов; рекомендуется UUID/ULID;
- `X-Auction-Signature`: lowercase hex HMAC-SHA256.

Подписываются точные байты (символ `\n` — один LF):

```text
auction-legacy-v1\n<TIMESTAMP>\n<REQUEST-ID>\n<RAW-HTTP-BODY>
```

Подпись вычисляется с `LEGACY_BRIDGE_SECRET`. Любое изменение timestamp,
request-id или raw body делает её недействительной. По умолчанию timestamp
принимается только в окне ±300 секунд, которое задаётся
`LEGACY_BRIDGE_MAX_SKEW_SECONDS`; часы producer и сервера должны быть
синхронизированы.

После успешной проверки подписи request-id атомарно записывается в ограниченный
in-memory cache. Повтор отклоняется, а при заполнении всеми ещё действующими
nonce новые запросы также отклоняются (fail closed). Размер задаётся
`LEGACY_BRIDGE_NONCE_CACHE_SIZE`. Cache локален процессу: для нескольких WSGI
процессов необходим общий атомарный nonce-store; без него запускайте ровно один
процесс моста. Не логируйте секрет, заголовки аутентификации или тело запроса.

## Отчёт об уязвимости

Не публикуйте секреты и персональные данные в issue. Передайте описание,
затронутую версию, шаги воспроизведения и ожидаемое влияние владельцу системы
по закрытому каналу.
